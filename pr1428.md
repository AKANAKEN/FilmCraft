## What

Fix the three signed Exp-Golomb boundary failures in `filmcraft-bitstream` (#1428), per H.264 9.1.1 / Table 9-3:

- `write_se(i32::MIN)` panicked with `attempt to multiply with overflow` (checked builds) — the codeNum mapping ran in `u32`.
- `read_se` accepted codeNum `2^32 - 1` (maps to `+2^31`, not representable) and returned `Ok(i32::MIN)` via wraparound.
- codeNum `2^32` (maps to the representable `i32::MIN`) was rejected because `read_se` narrowed through `read_ue() -> u32` first.

## How

Keep the raw codeNum in `u64` until the signed mapping is applied:

- New private `read_ue_raw() -> Result<u64>` holds the existing codeword parse (same 32-leading-zero limit); `read_ue` is now `u32::try_from` over it — **no behavior change for `ue(v)` callers**.
- `read_se` maps the raw codeNum (`odd → +(k+1)/2`, `even → −k/2`) in `i64` and rejects out-of-range results with `InvalidExpGolomb` via `i32::try_from`.
- `write_se` computes codeNum in `u64` (`-2i64 * v` for the negative branch), so `i32::MIN` → codeNum `2^32` encodes correctly through `write_ue_raw`.

Public signatures unchanged.

## Testing

Adds the reporter's three boundary tests verbatim plus a boundary roundtrip (`i32::MIN`, `i32::MIN+1`, `-1`, `0`, `1`, `i32::MAX-1`, `i32::MAX`):

- **Red on pristine main**: the 4 new tests fail exactly as the report describes (overflow panic; `Ok(i32::MIN)` for `2^32-1`; rejection of `2^32`).
- **Green with the fix**: `cargo test -p filmcraft-bitstream` → 12/12 pass.
- `cargo fmt --check` and `cargo clippy --all-targets` clean.

Reproduced at the library API level only; no application-level media repro claimed (matches the report).
